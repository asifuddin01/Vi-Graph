# Training (Colab T4 only)

All fine-tuning runs in **Google Colab on a T4 GPU** (spec §18). The backend never trains —
it only loads a saved LoRA adapter via `VIGRAPH_VLM_ADAPTER_PATH`.

| Path                                   | Contents                                                     |
| -------------------------------------- | ------------------------------------------------------------ |
| `notebooks/vigraph_qlora_t4.ipynb`     | **The notebook to run in Colab** (generated by `make_notebook.py`) |
| `notebooks/vigraph_qlora_windows.ipynb` | The same run on a Windows PC with a local GPU (VRAM capped, default ≈ 11 GB), plus Phase 7 sections: 9 = re-evaluation with 4096 output tokens, 10 = the fine-tuned model at 640 / 768 / 896 / 1024 px (§24B) |
| `configs/qlora_t4.yaml`                | Model, LoRA, quantization, schedule, checkpointing           |
| `qlora/`                               | Config, examples, loss masking, trainer, hand-back packaging |
| `tests/`                               | Tests for everything that doesn't need a GPU                 |

## How to run it

1. Open `training/notebooks/vigraph_qlora_t4.ipynb` in Colab (*File → Open notebook →
   GitHub*, or upload it). *Runtime → Change runtime type → **T4 GPU***.
2. Run the sections in order. Each has a short explanation at the top:

   | Section | What it does |
   | --- | --- |
   | 1. Setup | GPU check, mount Drive, clone this branch, install libraries, imports |
   | 2. Dataset | Build synthetic-v1 (deterministic) and verify its ground truth against the repo |
   | 3. Preprocess | Build training examples; check what the loss covers and the token lengths |
   | 4. Model | **Smoke run**: 4-bit model + LoRA, 2 steps, reload the adapter through the app's pipeline; projects the full run's duration |
   | 5. Train | The full QLoRA run, checkpointed to Drive — resumable |
   | 6. Evaluation | Zero-shot vs fine-tuned vs the classical baseline on the held-out test split — resumable |
   | 7. Save & hand back | One zip with everything to give back |

3. **After a disconnect:** reconnect, re-run sections 1 and 2 (they skip finished work),
   then the cell you were in. Training resumes from its last checkpoint; evaluation from its
   last finished sample. A run directory refuses to resume with a different config or a
   different data build.

## What to give back

`vigraph-handback-<run_name>.zip` from `MyDrive/vigraph/handback/` (section 7). It holds
the adapter, `training_run.json` (§18.1 metadata), the loss log, every evaluation run with
per-sample predictions, the paired comparisons, this data build's manifest, and a
`MANIFEST.json` (sizes, sha256, anything missing, environment). If something failed, send
the full error output of the failing cell instead (or as well).

## Design decisions

- **Same format as inference.** Training examples are exactly what the app sends: Stage A
  resize to `image_max_side` (1024), the `graph_extraction@1` prompt, the HF backend's chat
  format. The answer is the ground truth as compact JSON with nulls omitted (schema-valid,
  ~25% fewer tokens than with nulls).
- **Loss on the answer only**: labels are masked through the assistant header, which is
  derived from the model's own chat template. The notebook prints what is trained on.
- **QLoRA for a T4**: 4-bit NF4 weights with double quantization, fp16 compute (a T4 has no
  bf16), LoRA r=16/α=32 on the language model's attention and MLP projections (the vision
  tower stays frozen), micro-batch 1 × 16 gradient accumulation, paged 8-bit AdamW,
  cosine schedule, gradient checkpointing. These are starting values, not tuned ones (§18).
- **Never on the test split**: `load_training_split` refuses held-out splits.
- **Evaluation** uses the same runner as everything else (`python -m evaluation run`), on the
  same data build for all three conditions, so the comparisons are paired (§20.11).

## Troubleshooting

| Symptom | Try |
| --- | --- |
| pip warns `numba … requires numpy<2.3, but you have numpy 2.5.x` | An older notebook upgraded Colab's numpy. *Runtime → Disconnect and delete runtime*, then run from section 1 (it now pins Colab's numpy/scipy/pillow/torch) |
| CUDA out of memory | `data.image_max_side: 768` in the config (fewer image tokens); keep micro-batch 1 |
| Loss is `nan` / explodes | Lower `learning_rate` to `5e-5`; fp16 overflow is the usual cause on a T4 |
| Smoke-run label check fails | The model's chat template differs from what the collator expects — send the output |
| Very slow steps | Check the GPU is a T4 (section 1) and that sequences aren't huge (section 3) |
| `ResumeMismatch` | The config or the data build changed: use a new `run_name` for a new run |

## Rules

- 4-bit quantization + LoRA/QLoRA; no full fine-tuning, no training from scratch.
- Checkpoint to Google Drive frequently and support resume after disconnects.
- Log reproducibility metadata for every run (§18.1): model + revision, LoRA config,
  quantization, prompt hash, decoding params, seed, `schema_version`, split hash.
- Never train on the test split.

Adapters and checkpoints are not committed to git.
